# ホストからのWi-Fi設定・接続簡素化

2026-10-25 / R01 / **仕様・実現性調査のみ。未実装・実機未検証。**

対象: AtomS3R + Atomic Voice Base A149、端末・ホスト0.6.0-rc.1。
基準: `dec249696e84f97b63eba122f33dbb624edfd484`。
作業ブランチ: `codex/host-ap-provisioning`。

## 目的と範囲

スマホで行っているWiFiManager設定をWindowsホストの「スタックチャン接続」ボタンから行い、PCホットスポット経由の既存通信へ移行する。

今回の承認範囲は仕様・実現性・問題点の整理まで。ホストのコード変更、EXE生成、PCのネットワーク切替、端末への設定送信・書込み・USB監視は実施しない。RC1の公開物と動作仕様は変更しない。

端末ファームウェア、AP名`Stackchan-Setup`、既存のAPパスワード、呼びかけ登録、音声処理、通信プロトコルは維持する。**接続先ホットスポットのSSID・パスワードの保存は、従来のスマホ設定と同じ必要な変更**として扱う。「端末設定を一切変更しない」とは両立しない。既に正しい接続先が保存されていれば再送信しない。

## 結論と確度

**端末変更なしで実現できる見込み。ただしPC側のWi-Fi切替とホットスポットの維持・復旧を先に実証する必要がある。** 現行ソースの設定受付は確認できたが、このPCで全工程を自動化できるとはまだ断定しない。

| 区分 | 調査結果・意味 |
|---|---|

| 確認済み | 設定APは`192.168.4.1`。未設定時等に開き、設定失敗後もポータルを維持する構成。保存済みWi-Fiに接続できる通常起動は`autoConnect`であり、毎回APには入らない。 |

## 利用者の操作と内部処理案

利用者の操作は、①PCホットスポットを2.4GHzで有効化、②ホストを起動、③端末を起動して必要なら既存操作でWi-Fi設定画面へ入る、④「スタックチャン接続」を押す、を基本とする。保存済みAPIキー・モデル・採用済みの声を用いる。これらの初回設定は別途必要。

ボタン後の処理は以下の状態遷移とする。時間は初期案で、実機測定後に調整する。

| 状態 | ホストの処理 | 判定・失敗時 |
|---|---|---|
| 事前確認 | ホットスポット稼働、2.4GHz設定、受付IPv4/サブネット、ホスト実行条件、元のWi-Fi接続と復帰手段を確認。対象ホットスポットの資格情報をメモリへ取得。 | 不明・複数候補・権限不足なら切替前に停止して案内。既存の開始/停止/試聴と排他。 |
| 既存接続確認 | ホットスポット側だけで待受を開始し、既に参加済みの端末からの到達を短時間待つ（案: 10秒）。 | 到達が確認できればAP設定を省略。PC自身のヘルスチェックは端末到達に数えない。 |
| AP探索 | クリックに応じて`Stackchan-Setup`を探す。対象の識別とPCの復帰手段を確定する。 | 見つからない場合は設定画面への入り方を案内。複数BSSIDの同名APは自動選択しない。 |
| AP一時接続 | 対象Wi-Fiアダプタを指定し、既存AP認証情報で一時接続。元のプロファイルを上書きしない。 | 案: 30秒。キャンセル・失敗でも必ず復帰処理へ。ホットスポット継続不能なら後述の対応可否を判断。 |
| 設定画面確認 | 当該アダプタが対象APへ接続済みであること、AP側IPv4/経路、`192.168.4.1`のWiFiManagerフォームを確認。HTTPプロキシとリダイレクトを無効化。 | 別インターフェースやVPNへ流れる曖昧な経路、フォーム不一致なら資格情報を送信しない。画面本文は保存しない。 |
| Wi-Fi設定送信 | `POST http://192.168.4.1/wifisave`へ`s`/`p`だけをフォーム形式で送信。URLクエリに資格情報を含めない。 | 応答受付とWi-Fi接続成功は別判定。応答前のAP切断も「結果未確定」とし、再送前に復帰・参加確認する。 |
| PC復帰 | 元のWi-Fi接続へ戻し、ホットスポット・インターネットの状態を再確認。PC側IPv4/サブネットを再取得して必要なら待受を再開する。 | 案: 60秒。復帰不能はPC復旧が必要と明示し、成功扱いしない。APIキーやWi-Fi資格情報をエラーへ含めない。 |
| 端末到達待ち | 復帰後のホットスポット上で新しい端末由来の要求を確認する（案: 60秒）。 | AP消失・HTTP200・DHCP参加だけで完了としない。時間切れは設定失敗・PC復帰失敗と区別する。 |
| 完了 | 「端末からPCへの接続を確認しました」を表示し、従来の質問経路へ移る。 | 会話・音声・口パク・待受復帰の合格は別途実機で確認する。 |

停止時は未送信なら送信を中止する。送信済みなら端末の保存設定を自動で巻き戻さず、結果を未確定としてPC復帰を優先する。ウィンドウ終了も復帰処理が終わるまで待つ設計とする。アプリ強制終了時まで復帰を保証できるとはしない。

## 問題点と設計上の扱い

### 1. 無線アダプタとインターネット接続

PCが上流Wi-Fiを使っている場合、同じアダプタを端末APへ切り替えると上流接続が中断する可能性がある。モバイルホットスポットの継続可否もドライバ・構成依存として検証する。有線インターネットでも、Wi-Fi側のAP/STA同時動作が保証されるわけではない。

優先するのは、稼働中ホットスポットを維持して一時接続できる構成。実証できない構成では、別Wi-Fiアダプタの使用、または復帰後に端末が再接続する手順を比較する。ホットスポット停止を伴う方式は端末の15秒接続タイムアウト・ポータル残留との整合を実証するまで採用しない。単純に「停止→送信→再開」で必ずつながるとは扱わない。

### 2. Windows APIと資格情報取得

候補は`NetworkOperatorTetheringManager.GetCurrentAccessPointConfiguration()`によるホットスポットSSID/パスワード取得と、Native Wi-Fi APIによるAP一時接続・元のプロファイルへの復帰。旧Hosted Network向けコマンドとモバイルホットスポットを同一視しない。実装手段は未決定で、既存EXEへの組込み方法・追加依存・権限の検証が必要。

設定取得ができない場合、正しいホットスポットのSSID/パスワードの入力が必要になり、初回からの完全なワンクリックにはならない。Windows設定の不正確な推測、全Wi-Fiプロファイルの平文エクスポート、秘密情報のファイル保存は行わない。Wi-Fi APIが位置情報許可を要求するWindows環境では、クリック時に目的を説明し、拒否・アクセス拒否を通常の失敗として案内する。

### 3. 端末の識別と信頼の限界

同じSSIDと既存APパスワードだけでは、特定の個体を認証できない。フォーム確認やBSSID選択は誤接続対策であり、暗号学的な端末認証ではない。同名APを複数検出した場合は処理を止め、設定対象以外を停止して再実行する案とする。端末変更なしではこの認証上の限界が残る。

ホットスポット資格情報は設定対象APにのみ送信し、メモリ上で必要な間だけ保持する。コマンドライン引数、ログ、例外、設定JSON、ビルド成果物へ残さない。ローカル設定用HTTPは既存APのWi-Fi保護を前提とし、Gemini APIキーを端末へ送らない。

### 4. 「端末接続」の判定

現行の`device-online`は`/healthz`の受信を通知するが、個体IDや送信元IPをイベントへ含めない。PC自身やホットスポット参加中の別機器からの要求でも発生し得る。端末側`WirelessLink::online()`は成功後の状態を保持するため、毎回新たなヘルス要求が届くとも限らない。

ホスト側だけで新規のリモート要求・接続元・時刻を観測できるようにする案を検討する。DHCPクライアント情報を取得できる場合は補助証拠にし、個体認証の代わりにはしない。新規設定後の到達、既に稼働中の端末、複数機器、ヘルス要求再送なしをそれぞれ検証する。判定できない場合は「待受中」と表示し、接続成功を推測で表示しない。
