# StackchanHostの声質選択・指定 実現性検討

- 版数: R02
- 調査日: 2026-10-21（日本時間）
- 対象: StackchanHost 0.5.0-preview.1、Wi-Fi接続、Gemini Live API
- 目的: ホスト側で回答の声を選び、設定を保存してクラウドへの要求へ反映できるかを調べる。
- 状態: 文書・ソース・SDK型定義の調査完了。実装、ビルド、API要求、音声試聴、実機検証は未実施。
- 依存関係: Python/TkinterのホストUI、Node.js中継、@google/genai 2.30.0、対応するGemini Liveモデル。以下は提案であり、機能の実装完了を示さない。

## 結論

ホスト側への実装は可能と判断する。Google公式は、LiveセッションのspeechConfigで既成の声名を指定する方式を案内し、Koreを例示している。現在のSDKにも必要な型がある。現行ホストはその指定を行っていないため、UIだけでなく設定保存と中継への伝播を追加する必要がある。[公式Live API資料](https://ai.google.dev/gemini-api/docs/live-api/capabilities#change-voice-and-language)、[現行接続処理](../server/gemini-turn.ts)

「声モデルのプルダウン＋サンプルヒアリング」は、StackchanHostの正式な恒常仕様として必須とする。通常のプルダウンには対象Liveモデルで日本語を実聴確認した明示的な声IDだけを表示し、日本語に不適切な声と未評価の声は含めない。日常の声選択・試聴のためにホスト停止を必須とせず、声変更は進行中の会話に影響させず次の質問から適用する。現行の起動時固定設定から安全に更新する経路の追加が必要である。声の選択だけなら端末の再フラッシュは不要と考えるが、配布EXEの再生成と動作検証が必要である。声の切替が実APIで成功することは今回確認していない。

AIモデルは会話を処理するモデルの選択、声名はそのモデルの回答音声の選択であり、別の設定として扱う。声を変えるためだけにモデルやAPIキーを変更する必要はなく、既存の暗号化キー設定を保持する設計とする。

## 問題点と対策案

1. **モデルと声の対応範囲**: ホストはモデル名を自由入力できる。名前の書式が正しくてもLive非対応や声の非対応はあり得る。候補一覧は対象モデル・確認日を持って管理し、「公式で例示」「API受理済み」「日本語実聴合格」を区別する。日本語対応は全声の日本語品質が適切という意味ではない。現時点では合格・不適切の確定リストを作れない。Koreは公式例としての候補であり、合格済みとはしない。
2. **不正値・非対応時の表示**: 現行のCONFIG分類は要求設定一般のエラーであり、声名だけが原因と断定できない。指定したモデルと声を安全に確認できる案内が必要。APIの生のエラー本文・認証情報は表示・ログ保存しない。失敗時に勝手にAPI既定の声へ切り替えず、選択を保ったまま利用者へ知らせる。[現行エラー分類](../server/gemini-turn.ts)、[現行UI案内](../desktop/host_app.py)
3. **API既定と保存互換**: API既定は具体的な声IDを特定・固定できないため、将来の変更を含め、日本語確認済み一覧の保証ができない。通常プルダウンには含めない。声のない旧設定は移行対象として保持し、確認済み明示声の選択を促す。暗号化キーを保持し、未知の保存値を黙って置換しない。起動時環境変数、UI、実行中設定の優先順位を明示する。
4. **停止不要の反映経路**: 現行の起動時固定configから、次ターン設定を安全に更新する経路が必要。進行中の質問の設定を固定し、声変更と新規質問の競合を制御する。モデル変更時は合格一覧との組合せを再確認する。公式の声指定は接続時設定なので、接続中のセッション変更に頼らず、次ターンの新しいworkerへ適用する。日常の選択・試聴でもWi-Fi待受サービスを維持する。
5. **日本語の声質・安定性**: 同じプリセット名でも日本語の聞き取りやすさ、端末スピーカーとの相性、応答ごとの揺れは実聴が必要。評価では固定文の発音、明瞭さ、自然さ、言語の逸脱を確認し、合否理由を記録する。声選択は発話冒頭の欠けを解決する機能ではなく、端末の発話前約0.2秒待機は別ToDoのままとする。
6. **必須のサンプルヒアリング**: 本会話と同じLiveモデル・声IDと、全候補で同じ日本語固定文を用い、PCの現在の標準再生先へ再生する。アプリは音量・出力先を勝手に変更しない。試聴操作時だけAPIを使い、選択・起動・一覧表示ではAPIを呼ばない。停止・再試行・エラー表示・二重要求防止と、利用枠消費の案内が必要。試聴は待受・停止中に行い、会話処理と重ねない。試聴中に質問が届いた場合の優先順位を定め、勝手に同時再生しない。
7. **PC再生と固定文の制約**: 現行は返却PCMを端末へ送る構成であり、PCへ再生する経路、音声出力不可・ミュート等の案内を追加する必要がある。通常の「短く一文で回答」という指示では試聴文をそのまま発話する保証がなく、試聴用の指示を別に持つ。Liveは対話用途のため、同一文の再現性も実APIで確認する。同じ声でも発話の揺れは残り得る。

## 恒常仕様と検証方法

日本語実聴合格済みの明示声だけのプルダウン、選択保存、次質問からの適用、必須のサンプルヒアリング、無効指定時の明示エラーを恒常仕様とする。通常画面の自由入力は確認済み一覧を迂回するため設けない。表示は声の特徴を過度に断定せず、正式な声名と対象モデルを確認できる形とする。試聴で選好を確かめられることと、日本語品質の事前評価に合格した候補だけを表示することは別の要件である。

対象モデル・API・アプリ更新時は日本語適性を再評価する。恒常機能の仕様は[正式仕様R01](STACKCHANHOST_VOICE_SPEC.md)を参照する。

実装後のオフライン検証では、旧設定の移行、明示声IDの保存・再読込み、確認済み候補だけの表示、環境変数からNode・子worker・接続設定までの伝播、次ターン更新の競合制御、進行中の会話の設定保持、エラーとフォールバック禁止を確認する。試聴の開始・停止・再試行・二重要求防止、本会話との排他制御、APIを自動送信しないことも確認する。既存のAPIキー暗号化と同梱秘密情報検査を維持する。

実API検証では候補ごとに対象モデル・声ID・同じ日本語固定文・確認日・合否理由を記録し、日本語に不適切な声を除外する。未評価は不適切と断定せず候補未採用として扱う。PC試聴と端末の会話が同じモデル・声IDを使うこと、停止不要で次の質問から変更が反映されること、再起動後の復元を確認する。その後、USB制御・監視なしでウェイク→質問→回答音声→口パク→待受復帰を確認する。不正な声名・非対応モデルの検証もAPI要求を伴うため、実装後の検証計画で範囲を決める。

今回の確認は資料と現行ソースの整合性までであり、声の実際の切替、音質、待ち時間、冒頭欠けへの影響は未検証。コード生成・コード編集・ビルド・API送信・実機操作は実施していない。
