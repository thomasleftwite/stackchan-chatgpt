# R07: 準備完了後のビープと0.7秒後の発話受付

2026-10-19（日本時間）/ R07。対象: AtomS3R + Atomic Voice Base A149、Arduino-ESP32 2.0.17、PlatformIO atoms3r-gemini-device。依存固定版はplatformio.ini。目的: 利用者の指示に従い、登録3回と通常質問の両方を「準備→ビープ→0.7秒→発話受付」に統一する。画面を見て追加の準備終了を待つ必要をなくす。

## 変更する順序

1. ビープを鳴らす前に、マイクを起動して初期400msを捨て、600msの環境音を測定する。雑音/取消/故障なら開始ビープを鳴らさず終了する。
2. 準備が通った後、マイクを停止し、従来の開始ビープ500msを最後まで再生する。
3. ビープ終了直後にマイクを再起動し、終了後700msまでは入力を捨てる。この700ms内で起動直後の過渡入力の除去を済ませる。環境音測定をやり直さない。
4. 700ms経過時に発話受付へ移る。以後に届く音声を準備前に測った閾値で判定する。録音開始後に追加のPreparing期間を設けない。

Preparingはビープ前に終了する。ビープと700msの待機中はGet readyを表示し、その後に登録はLearning call、質問はListeningへ移る。音声受付の境界は完了コールバック側で記録し、前景の描画が遅れても700ms後に届いた入力を捨てない。

700msは「マイクを停止したまま待つ時間」から「ユーザーが発話を待つ時間」へ変える。これは今回の明示指示による順序変更で、R06以前の試験条件を置き換える。ビープ中はマイクを停止し、終了後700msより前の完了フレームを録音窓/特徴/APIへ渡さない。連続録音の要求を維持し、発話の冒頭を失う追加の1秒校正を行わない。フレーム境界は20ms単位で、開始境界をまたぐ未完了フレームは冒頭保護のため残す。

登録3回の相互照合/代表選択/自動保存、旧登録保護、品質閾値、通常の待受・Sleep・PC接続仕様は維持する。アプリ限定導入でR06の保存済み登録と設定を保持する。通常質問の本文だけがGeminiへ送られ、登録音声や呼びかけは送らない。

## オフライン検証

ビープ後700msに600msの音声を話す2つの試験を先行追加。R06保存ソースを使う.pio/device-check/run_r07_before.pyで登録/質問の2/2失敗を再確認し、R07の実ソースで2/2成功した。質問試験はWakeWaitから実際のrecordQuestionへ入る条件を設定している。

登録UI28/28、保存29/29、録音品質13/13、FaceUI27/27、質問UI6/6、共通ルール27/27、PC監視17/17、固定状態許可リスト2/2で合計149項目成功。ビープ後650msまでの大きな過渡入力がモデル/API入力へ入らず、700ms後の声が残ること、準備中/700ms待機中/録音中の取消、700ms内に再起動できない場合の失敗、3回登録/再試行を含む。旧「マイク停止の700ms」を前提とする試験は今回のユーザー指示に合わせて置換した。

再現はtools/run_host_tests.pyのwake-enrollment-ui/wake-storage/wake-enrollment/face-ui/gemini-ui/rulesとunittestのtest_enrollment_status.py/test_gemini_coordinator.py。FaceUIの準備失敗試験は、準備前のビープが出ないことを要求するよう変更。新しいGet readyを含む19モードのSVGを生成した。サーバと配布EXEは今回変更/再生成していない。

通常版atoms3rと端末版atoms3r-gemini-deviceのビルド2/2成功。端末版RAM58,104 bytes、ELF flash1,471,377 bytes。仕様/品質の独立した読取レビュー2軸で修正必須の指摘なし。ビープ中のマイク停止、producer側の境界、6400サンプル以上の圧縮余裕、質問側の抽出offset、取消時の停止順を確認した。実機のマイク再起動時間と700ms基準の発話品質は別途確認する。

状態監視5652の終了後、PCサービス/端末の単一セッション71704を起動。利用者に画面を待たず、呼びかけ後のビープ終了から約700msで質問する通常操作を2回依頼し、「2回とも回答が聞こえ、Readyへ戻った」と確認できた。WAKE MATCHは2回、API結果はPASSが2回、端末の一意なRESULTはgen1/2ともPASS・played=1。状態照会での同じRESULTの再送は新しい成功として数えない。
