# 第3段階R06: 同じ操作3回で呼びかけを登録

開始合図の現行仕様は[R07](WAKE_STAGE3_R07.md)。準備をビープ前に済ませ、ビープ終了700ms後に発話できる。本書は3回登録の設計・R06の実機履歴。

2026-10-19（日本時間）/ R06。対象: AtomS3R + Atomic Voice Base A149、Arduino-ESP32 2.0.17、PlatformIO atoms3r-gemini-device。依存固定版はplatformio.iniを参照。目的: 利用者の要望に従い、録音・別操作の照合・保存確認を分けていた複雑な学習手順を、同じ操作3回と自動整合確認へ置き換える。

## 操作と整合性

Sleepingで画面ボタンを約7秒長押しして離すと登録へ入る。1/3、2/3、3/3のそれぞれで短押しし、開始音と準備を待ち、Learning callの発話案内で同じ呼びかけを話す。3回とも同じ操作・画面を使う。各回のビープ完了後700ms待ち、初期400ms破棄と600ms環境音測定は維持する。

3回分の特徴をRAMで保持し、全3組のDTW距離が既存wakeThreshold未満であることを確認する。一致した3回のうち他の2回との距離合計が最小の代表特徴を既存の1パターン形式で保存する（同点は先の録音）。複数モデルを並列に検出する方式にはしない。最終保存確認の短押しは省き、3回が整合したら自動登録する。

3回終了前、品質不足、整合不一致、保存失敗では旧登録を維持する。失敗理由を表示してから短押しで最初の録音からやり直せる画面を出す。長押し2秒（案内は約3秒）または無操作30秒で取消。開始した各録音中はボタン押下で取消。全特徴と録音バッファは終了時に解放/消去する。録音と特徴はGoogleへ送信せずログにも保存しない。

## 初回実機試験と無言試験

利用者はRoom too noisyを報告。最初の試行と短押しでの再試行は計6回すべてrecord1の準備でNOISYとなり、発話録音に入らなかった。CAL rmsは3131/2976/2034/1843/1438/2011、gap727〜728ms、校正1040〜1041ms、録音窓samples=0/voiced=0。この結果を3回の相互照合失敗とは扱わない。短押し再試行自体は実機で機能した。

続いて発話せず10秒待つ試験を案内。CAL rms=329 threshold=987 ms=1039 gap=728で準備を通過し、Learning call/mic=1へ入り、無発話のためNO_SPEECHで再試行画面へ戻った。少なくともこの回では開始音後の700ms待ちと環境音測定が成立した。先行6回の入力音が環境音/準備中の発話/端末音のどれだったかは未確定。雑音基準や待ち時間は変更していない。3回連続の録音/自動保存はまだ未確認。

追加の無言試験もCAL rms=242 threshold=750 ms=1040 gap=728で通過し、NO_SPEECHになった。利用者も無言で待ち終わったと回答。無言時は2回連続で準備が通過したため、Learning call表示まで無言を保ってから各回発話する3回登録を案内している。

その後の3回もCAL rms147/220/113、gap728msで準備を通過したが、すべてvoiced=0のままNO_SPEECHとなった（合計NOISY6/NO_SPEECH5/SAVED0）。利用者は別の表示と回答しているため、追加操作を止め、上段/下段の実表示とLearning call後に発話できたかを確認中。3回整合確認にはまだ到達していない。無言試験の通過から雑音原因が解消したとは断定しない。

利用者から「無音を3回試す指示だったので発話していない」と確認できた。上記NO_SPEECHは指示どおり無言で試した結果で、発話を取り込めなかった不具合の証拠には使わない。こちらの案内で無言試験と発話登録試験が混在したことを訂正し、無言試験の準備通過を確認済みとした。次は同じ呼びかけを3回話す登録だけを案内する。ファームウェアの変更・再書込みは行わない。

## 発話を伴う3回録音の到達

監視49481の終了を確認後、単一監視セッション2026で.pio/device-check/face-stage3-r06-live-20261019-r02.jsonへ継続。初期に再照会したNO_SPEECH/CAL113は前回試験のRAM保持値で、新しい試行には数えない。

準備時NOISYと再試行の後、3回すべての録音が成立した。record1はCAL276/828、samples20160/voiced9280/ms3219、record2はCAL201/750、samples21440/voiced10880/ms3315、record3はCAL79/750、samples22400/voiced11520/ms3267。3回ともgap728ms・校正1040ms。STEP checkからMISMATCH、STEP retryへ進み、保存は行われなかった。実機で3回録音→整合確認→不一致時に旧登録を保持してやり直す流れを確認した。整合して自動保存する経路は実機未確認。NOISY時の音の発生源も未確定。

## 3回の整合確認と自動保存成功

続く試行でrecord1→record2→record3→check→save→SAVEDの順に進み、Sleep/mic=0へ戻った。証跡はr02.jsonの149187〜172406ms。各回の固定数値は次のとおり。

| 回 | 環境音RMS / 閾値 | 校正ms / ビープ後待ちms | 保持samples / 有声samples | 録音処理ms |
|---|---|---|---|---|
| 1/3 | 163 / 750 | 1039 / 728 | 22720 / 12160 | 3267 |
| 2/3 | 261 / 783 | 1039 / 728 | 21760 / 10880 | 3315 |
| 3/3 | 59 / 750 | 1040 / 728 | 21440 / 11200 | 3267 |

全3組の整合判定と代表特徴のファイル保存/全特徴読戻し照合が成功したことをSAVEDで確認した。最終保存クリックは不要で、Googleへは送信していない。利用者によるCall saved表示の確認、再起動後の保持、通常呼びかけ/質問回答への回帰はこの時点では未確認。これを雑音発生源の特定や精度保証とは扱わない。

## 再起動後の確認

利用者が本体リセットボタンを短押しし、Sleeping表示を確認。リセットに伴い状態監視2026はusb_errorで終了した。これは既知の物理リセット時のUSB再列挙を伴う今回の観測であり、保留中の接触不良調査の再発証拠には使わない。

serverの既存コードを再ビルドして成功。既存run_gemini_device.pyで一時PCサービスを起動し、COM4へ接続。セッション43342、最大580秒、終了時に.pio/device-check/face-stage3-r06-postreboot-20261019-r01.jsonへ固定状態と数値だけを保存する。BUILD enrollment=6、configured=1/wifi=1/pc=1、Sleep/mic=0、ENROLL CAL/result/AUDIO NONE・STEP noneを確認し、前回のRAM状態が消えた再起動後の接続と区別した。質問しなければGoogle呼出しは行わない。再登録/フラッシュ/設定ファイル更新は行っていない。

次に短押しReady→登録した呼びかけ→Listeningで短い質問→回答/Ready復帰の1回を依頼した。質問だけをGeminiへ送信する通常経路の試験で、呼びかけは端末内に留める。実検出と回答の結果は追記する。

GEM WAKE MATCHを取得し、再起動後に登録が読まれて実際の呼びかけを検出できたことを確認した。最初の質問準備はCAPTURE NOISYで終了したが、その後CAL rms319/threshold957、CAPTURE DONE input26880/captured44800/clipped0を取得。PC処理PASS（入力26880、出力78240サンプル、API処理7892ms）、端末RESULT PASS gen=1/frames163/ms17337/played=1を確認した。利用者も「回答が聞こえ、Readyへ戻った」と回答。API時間と端末の処理時間は区別する。

続いてReadyのままもう一度同じ呼びかけ→質問→回答/Ready復帰を依頼し、回答後の検出再開を確認する。質問1回目後のGEM PC OFFLINE行も記録されているが、まだ完了前のセッションなので終了記録と後続状態を合わせて確認する。常時ネットワーク監視の追加やUSB接触不良の原因究明の再開は行わない。

2回目の確認途中で利用者が開始音の順序変更を指示したため、そちらを優先して[R07](WAKE_STAGE3_R07.md)へ進んだ。一時サービス43342はuser_stop/code0/serverCode0/deviceStopConfirmed=trueで正常停止。保存済みr01.jsonにAPI成功1回と端末gen1の再生成功を確認した。途中のPC OFFLINEだけをサービス終了やUSB異常の証拠には使わない。R06として回答後の2回目再検出の利用者確認は未完了。
