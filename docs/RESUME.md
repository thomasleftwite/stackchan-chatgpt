## 現在地

最新のホスト実装は[声選択・PC試聴0.6.0-preview.1](STACKCHANHOST_VOICE_IMPLEMENTATION_2026-10-21.md)。Python47/Node37成功、独立2軸レビューの指摘修正。通常リストには採用済み声だけを表示し、未評価声は別画面でPC試聴→利用者が採用する。最新0.6.0-preview.2はPC試聴だけで即時一覧追加・選択・保存する（端末確認不要）。[修正・検証記録](STACKCHANHOST_VOICE_PC_ADOPTION_2026-10-21.md)。日本語合格声はまだ0件で、実API/実PC再生/品質は未確認。ホストだけ更新し、試聴時は利用者が端末をSleepingにする。端末の追加更新やUSB監視はなし。発話前0.2秒ウェイトは[端末へ導入済み・実聴待ち](REPLY_START_DELAY_2026-10-21.md)。

**Windowsホスト0.5.0-preview.1 + AtomS3R無線版で、コード入力なしの接続から呼びかけ・回答再生・口パク・待受復帰まで基本確認済み。端末リセット後も自動接続し再会話できた。** 長期試験を含む製品完成とは扱わない。

端末はM5 AtomS3R + Atomic Voice Base A149。Arduino-ESP32 2.0.17 / PlatformIO Espressif32 6.11.0。ライブラリは [platformio.ini](../platformio.ini)、PC依存は [package-lock.json](../server/package-lock.json) に固定。配布EXEはPython 3.14.4 / Node 24.15.0を内蔵する。

**追加のUSBなし第一段階試験はウェイク開始が未達。** 利用者は手動長押しからの会話を複数回確認した一方、本来のウェイクワードを見逃し、リモート会議話者の声でListeningへ誤移行すると報告。過去の基本成功を、この環境の検出精度の保証にはしない。[調査記録](WAKE_DIAGNOSIS_2026-10-21.md)。登録/検出の発話基準差と単一テンプレート照合を優先調査対象とし、一時マイク失敗の継続停止もオフラインで再現。今回USBアクセス・実API追加・登録変更・実装修正・導入はなし。次はUSBに依存しない判定情報の可視化と、背景音声を含む照合条件の評価が必要。

直前の復旧元は[ウェイク診断・録音整合版R01](WAKE_DIAGNOSTIC_FIRMWARE_R01.md)。承認とUSB接続確認後にCOM4のアプリ領域だけへ導入、書込みハッシュ成功。登録と共通の環境測定/切出し、連続取得、再試行、Readyでの理由・V/T/D表示を追加。C++163項目/3構成ビルド成功。ホスト0.5は変更なし。書込み後のUSB監視は行わず、利用者のUSBなし起動/接続/呼びかけ会話確認待ち。以下の旧端末スナップショットは復旧元として保持。

- 端末内: SimpleVoxのMFCC/DTWで呼びかけを検出。3回録音の整合確認後に保存する。顔表示、発話終了判定、半二重の録音・再生を担当。
- 端末 ⇄ PC: Windowsの2.4GHzモバイルホットスポット。端末はDHCPゲートウェイのTCP48443へ自動接続する。アドレスは固定しない。
- 参加の確認: Wi-Fiパスワードで接続した機器を信頼する、という利用者指示に変更。通常経路はHTTP/WSで、アプリ独自TLS・Bearer・4行コードを使わない。PCはホットスポット側IPv4だけで待受し、HTTP/WSの接続元を同じサブネットへ限定。同じホットスポットへ参加できる機器も利用できる。
- PC ⇄ Gemini Live: Node.js中継が16kHz/16-bit/monoの質問音声を送信し、24kHzの回答を端末へ返す。1質問1回答。APIキーはPCだけで使い、任意保存にはWindows DPAPIを使用。登録音声・呼びかけは送信しない。
- 保存: 端末更新はアプリ領域だけに限定してWi-Fi・呼びかけ登録を保持。旧NVS認証鍵・PCのpairing.jsonは未使用のまま保持。USB診断経路は開発用として残す。
- Raspberry Piは将来候補。今回はWindows版の開発を継続し、Pi設定・クラウド公開・追加の自動監視は行わない。

## 確認済みと未確認

既存の最終コード検証はPython39件、Node32件、C++145項目、PlatformIO3構成、最終EXE自己診断11項目が成功。自己診断はAPI呼出し0回で、実会話とは別の検証。詳細・再実行手順は [HOTSPOT_TRUST](HOTSPOT_TRUST.md)。今回の資料整理ではアプリを変更せず、これらを再実行していない。

実機では利用者が3回登録のCall saved、呼びかけ反応、回答音声、口パク、待受復帰を確認。端末で照合距離188/MATCH・質問PASS/played=1、リセット後は距離187/MATCH・再会話PASS/played=1を確認。質問受付境界700/701ms。今回の再登録3回すべての受付境界を個別収録したとは扱わない。

未確認は、長期の検出精度・誤検出率、物理的な電源断耐性、別PCへの移行、長時間・切断等の異常系、連続ストリーミング・会話履歴。Raspberry Piホストは未実装。端末リセットの成功を電源断試験へ読み替えない。USB接触不良の原因追跡と追加のPC停止監視は利用者の指示・合意で保留。

再開後に接続台数0の不接続報告があり、給電切離し10秒後の再投入でPC Onlineへ復帰。その後のリセット単独再試験では、利用者が約5秒でPC Online / Sleeping、60秒後の接続台数1、呼びかけ・回答音声・口パク・待受復帰の成功を確認した。今回の1回の成功は利用者観察によるもので、失敗原因・再発条件・反復成功率は未確定。端末ログの追加取得とコード変更はなし。[再試験記録](HOTSPOT_TRUST.md)。

## 再開・動作確認

1. PCをインターネットへ接続し、2.4GHzモバイルホットスポットをオンにする。端末の保存済み接続先がPCホットスポットと一致していることを確認。
2. [ホストEXE](../releases/StackchanHost-0.5.0-preview.1-win-x64/StackchanHost.exe)を開く。「Wi-Fi（USB不要）」→「再検出」→ホットスポット側アドレス→Gemini APIキーを画面で確認→「接続して開始」。コード入力は不要。表示が空ならホットスポットを確認し、上流Wi-Fiのアドレスで代用しない。
3. 端末を短押しで起こし、登録済みの呼びかけ→ビープ終了から約0.7秒後に質問する。手動質問は起きた状態で約2秒押し、「Release to ask」で離す。
4. 必要な場合だけ再登録: スリープから5〜6秒押して離す。短押し→ビープ終了→約0.7秒後に同じ呼びかけ、を3回。保存成功まで旧登録を保持する。

詳細な初回Wi-Fi設定・終了方法は [利用手順](../desktop/README.ja.md)。最終実機確認時はホスト/ホットスポットを通常利用のため起動継続し、観測用USBは閉じた。現在の稼働はこの資料整理では再取得していない。キーやWi-Fi情報はチャット・公開資料へ記載しない。
